# Multiplayer, and whether to move to Godot

*Researched November 2026. Version numbers and prices change, so re-check the linked pages before acting on them.*

## The short answer

**For multiplayer, staying in TypeScript and the browser is the faster path. Godot is a good engine, but moving to it means rewriting the game, not importing it.**

- Toybox Mayhem is about 18,000 lines of TypeScript on three.js (graphics) and Rapier (physics), and almost everything (maps, toys, weapons, sounds) is generated by code. There is no tool that converts a three.js project into a Godot project. The **3D shapes** can come across: `__toybox.exportMapGLB()` (see below) saves a map as a `.glb` that Godot imports directly. Everything else (movement, weapons, bots, menus, modes) would have to be written again in GDScript.
- In the browser, a Godot game can't use Godot's usual networking (ENet, which needs raw UDP). Web builds have to use WebSockets or WebRTC, which is what this game can already do from TypeScript.
- The multiplayer groundwork already in this repo (below) works today: two players in the same room see each other move.

Godot becomes the better choice if you want **downloadable desktop or console builds**, a **visual editor** for building levels by hand, or to learn Godot itself. If you go that way, treat it as "Toybox Mayhem 2 in Godot", reuse the exported models and all the design numbers in `weaponConfig.ts`, and rebuild the code.

## What's already built (multiplayer groundwork)

| Piece | File | What it does now |
| --- | --- | --- |
| Message format | `src/net/protocol.ts` | Every message type the client and server send. Packed input frames (buttons in one number), player state, snapshots, ping/pong, chat. `PROTOCOL_VERSION` guards against mismatched builds. |
| Browser client | `src/net/NetClient.ts` | One WebSocket to the server. Reconnects with back-off, measures round-trip time and clock offset, and keeps a snapshot history per remote player so they can be drawn ~100 ms in the past, smoothly (snapshot interpolation). |
| Dev server | `server/index.mjs` (`npm run server`) | Node + `ws`. Rooms of up to 8, player ids, a 20 Hz snapshot broadcast, input validation and clamping, idle kick. Right now it is a **relay**: it trusts each client's own position. |
| Game hook | `Game.net` | While connected, the game sends your position, aim, health and weapon 20 times a second. |
| Model export | `Game.exportMapGLB()` | Saves the current map's geometry as `toybox-<map>.glb` for Godot or Blender. |

Try it:

```bash
npm run server          # terminal 1: ws://localhost:8787
npm run dev             # terminal 2: the game
```

Then, in the browser console during a match: `__toybox.net.connect('ws://localhost:8787', 'Me', 'room1')`. Open a second tab, connect it to the same room, and `__toybox.net.remotes` / `__toybox.net.sample(id)` show the other player moving. Other players aren't drawn in the world yet; that's step 1 below.

## Roadmap if you stay in TypeScript (recommended)

1. **Draw remote players.** Spawn a `ToyRig` for each entry in `net.remotes` and place it from `net.sample(id)` every frame.
2. **Lobby screen.** Server address + room code on the Play screen, a player list, a "ready" button.
3. **Make the server authoritative.** Clients send `input` frames instead of `state`, and the server runs the match. Rapier and three.js's math both run in Node, so `Actor`, `Combat` and the match rules can be shared between browser and server instead of rewritten. This is what stops cheating (a relay server will believe anything a client says).
4. **Prediction and reconciliation.** Your own toy moves instantly from local input; when the server's snapshot arrives, replay the inputs it hasn't seen yet. Hitscan hits are checked on the server against where targets were when you fired (lag compensation).
5. **Online accounts.** Replace `LocalAccounts` (`src/core/Accounts.ts`, which implements the `AccountService` interface the menus use) with one that talks to the server. Passwords get hashed on the server (bcrypt/argon2), and coins and unlocks are awarded by the server so they can't be edited in the browser.
6. **Hosting.** A browser page served over HTTPS can only open `wss://` (encrypted) connections, so the server needs a domain and TLS certificate, on a small VPS or a hosting service.

**Colyseus** is worth a look for steps 2–5: it's an open-source Node framework for authoritative game servers with rooms, matchmaking and state sync, and its official examples include a three.js first-person shooter with predicted movement, reconciliation and lag-compensated hitscan. Moving the dev server to Colyseus later would be a contained change, since `protocol.ts` and `NetClient` keep the rest of the game away from the transport.

## If you move to Godot

**Engine:** Godot 4.7.2 was the current stable release when this was written (August 2026); 4.8 was in beta.

**Editing Godot projects in VS Code:** use the official **godot-tools** extension (`godotengine/godot-vscode-plugin`). It supports Godot 4 fully.
- It talks to the Godot editor's GDScript language server (default port 6005) for autocomplete and errors, so the Godot editor must be open on the project. On Godot 4.2+ it can instead start a windowless "headless" editor for you.
- Debugging GDScript works from VS Code's Run and Debug panel (debug adapter, default port 6006) via a `launch.json`.
- If F5 can't find Godot, set `godotTools.editorPath.godot4` to the Godot executable.

**How I (Claude) can work on it from VS Code:** Godot scenes (`.tscn`), resources (`.tres`) and scripts (`.gd`) are plain text, so I can read and edit them, run Godot headless from the terminal to check scripts and run tests, and export builds. I can't see or click inside the Godot editor window, so hand-placing things in the editor is yours to do; describing levels in code (like this project does) keeps that to a minimum.

**Port plan, in order:**
1. Export each map with `__toybox.exportMapGLB()` and import the `.glb` files into Godot. Repeat for toy and weapon models (same approach).
2. Recreate the data: weapon and ability numbers from `weaponConfig.ts` become Godot Resources.
3. Rebuild player movement on `CharacterBody3D`, hitscan on raycasts, bots on `NavigationAgent3D`.
4. Multiplayer with Godot's high-level API (`MultiplayerSpawner` / `MultiplayerSynchronizer`, RPCs). Use ENet for desktop builds and `WebSocketMultiplayerPeer` for web builds. Browsers can't host, so web players always need a dedicated server.

## Comparison

| | Stay in TypeScript | Move to Godot |
| --- | --- | --- |
| Work to get back to today's game | none | full rewrite of gameplay, UI and bots (models can be exported) |
| Runs in a browser | yes, already | yes (web export), with WebSocket/WebRTC networking only |
| Desktop/console builds | via a wrapper (Electron etc.) | native |
| Level editing | in code | visual editor plus code |
| Multiplayer building blocks | done: protocol, client, relay server; next: authoritative server (Colyseus optional) | built-in high-level API; still needs a dedicated server for web players |
| Claude can edit and test it | fully, including in the browser | code and scenes as text, headless runs; not the editor UI |
